# 第一版产品范围与实施顺序

## 用户与工作边界

第一版供公司内部工程师使用。目标平台是已部署 EDA 的 CentOS 7 x86_64 桌面，主入口为 TUI，中文输入和粘贴在本机完成。保留旧 `opencode-centos7` 入口。

已知基础：现有兼容包能够运行 OpenCode、调用百炼模型，且已有第二位使用者另一位实习生的成功使用反馈。这证明已有跨用户复用基础，不等于新产品已部署、任意机器兼容或版图质量已达标。

### 当前第一项：启动页品牌定制

按用户最新要求，先完成公司 Logo、产品名称和启动页任务提示的定制，作为产品的首个可见交付项。启动页和 XunChi 标题已由用户在 CentOS 7 确认；brand.3 的退出乱码修复也已由用户反馈确认。实施与验收范围见 [启动页品牌定制](BRANDING.md)。

随后推进下面的执行和验证能力；页面品牌完成不代表这些能力已经实现。

### 核心功能优先：让执行可信

此前出现过 agent 发出命令却没有可核实输出，后续又推断文件被回滚的情况。产品应从机制上返回任务是否启动、是否仍在运行、真实退出码和新产物，避免工程师靠模型叙述猜测。

1. 完成部署配置和启动检查，区分 OpenCode 环境与 Cadence/Calibre 环境。
2. 将现有任务执行原型接入 OpenCode 自定义工具。agent 提交任务获得 job ID，然后查询；长任务无需持续占用一次 Bash 工具调用。
3. 复用现有 bridge，校验认证、Virtuoso PID、工程和实际 PDK 路径。端口占用先判断归属，不自动杀进程，也不反复新建 Virtuoso。
4. 把 CDL 导出、GDS 导出和 DRC/LVS 分别实现为受控动作。配置由工具生成和检查，不再让模型每次临时拼接整段命令。

**验收**：在目标 CentOS 中，模型独立提交一次导出和一次验证，用户无需代跑终端命令；中途离开对话后仍能查询结果。刻意制造配置错误、超时和 LVS 不一致，均返回相应状态与实际日志。

### 同期优先：修复日常输入和输出

1. 在固定上游提交上应用 OSC52 可关闭补丁，保持本地剪贴板辅助程序路径。
2. 在构建机重新生成内核并重新执行 CentOS 兼容适配验证；不直接修改现有可执行文件字节。
3. 为中文输入、长文本粘贴、复制最后回复、导出会话分别建立实机测试。
4. 提供稳定的 UTF-8 文本导出入口，避免工程师反复截图。

**验收**：中文输入成功；复制中文和多行输出后可在 gedit 正确粘贴；OpenCode 输入框不出现 `52;c;...`；重启后仍可用。补丁未编译进入实际内核前，不把环境变量开关称为已修复。

### 第二阶段：管住工程身份与修改过程

1. 工程配置明确源原理图和目标 Library / Cell / View、磁盘目录及 PDK。
2. 修改前记录原件和工作副本身份；写操作在明确的工作副本上执行。
3. 每次修改生成对象、层、坐标、单位及前后差异；保存后独立查询读回。
4. 将 OA 状态、导出 GDS、源 CDL、层映射和验证规则的版本信息关联到本次运行。
5. 原件回退、重新打开目标版图和任务恢复由工具支持，不依赖模型猜测。

**验收**：工程师根据报告能直接打开正确版图；工具能检出目标错位、未保存、PDK 堆栈错误和验证输入过期。不能用 GDS 哈希变化单独证明几何改动，也不能用 OA 的 net 名称代替物理提取与 LVS。

### 第三阶段：形成工程师能够使用的完整版本

1. 自研 agent 指令和工具默认配置随包交付，界面显示 xunchi 产品名、版本和上游来源。
2. 一次安装完成命令入口、依赖检查和必要配置；正常使用不再要求编辑配置文件。
3. 提供内部版本包、版本清单和回退包。旧入口与现有设计保持可回退。
4. 先由两名工程师在各自环境上完成相同任务，再扩大内部试用。
5. 公司确定源码仓库归属、负责人和使用许可，再决定是否向外发布。

**验收**：新同事按内部说明能够安装和使用；任务、输入、报告和回退均通过目标机测试。此时才将版本标为内部试用版，而非当前开发底座。

## 第一版不承担的能力

不把“一键完成任意模拟电路版图”作为第一版承诺。器件匹配、对称布局、寄生优化及自动 DRC 修复，放在执行、身份和验证闭环稳定以后，以实际任务逐项扩展。

## 如何说明产品价值

对同一个工程，记录改造前后：

| 指标 | 记录方式 | 直接对应的问题 |
|---|---|---|
| 用户代跑命令次数 | 每次任务人工接手计数 | agent 是否真正执行 |
| 启动到模型可用时间 | 从入口执行至收到第一条有效回复 | 启动是否方便 |
| 导出/验证完成率 | 完成并可查询的运行数 / 总运行数 | 任务是否可靠 |
| 结果误判次数 | 将未执行、超时或不一致报告为通过的次数 | 结论是否可信 |
| 版图目标可追溯率 | 完整身份及路径可读回的修改数 / 修改总数 | 能否找到正确版本 |
| 第二位使用者复现结果 | 同一流程在另一位工程师机器上验收 | 是否可交付 |

先采集基线，不预先编造“提速多少”或“减少多少成本”。

更新状态（2026-10-16）：用户已确认 CentOS 7 中退出不再出现乱码，且当前 agent 可以操控 Virtuoso。此反馈不替代系统剪贴板、完整工具封装或设计质量验收。内部包没有附于本次公开源码更新。
